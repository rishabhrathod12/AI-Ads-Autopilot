# API Design

## 1. Conventions
- Base path `/api/v1`; JSON; OpenAPI generated by FastAPI is the source of truth.
- Auth: `Authorization: Bearer <JWT>`; tenant derived server-side.
- Errors: RFC 7807 problem details (`type`, `title`, `status`, `detail`, `request_id`).
- Pagination: `limit` + cursor. Dates: ISO 8601. Money: integer paise + `currency`.
- Every data response includes `data_source` and `as_of` so the UI can show MOCK labels.
- Rate limits per user/tenant; stricter on LLM endpoints; `429` with `Retry-After`.

## 3. Authorization matrix
Viewer: read. Analyst: read + generate recommendations + assistant. Admin/Owner: approve/reject, sync, audit. Deny by default.

## 4. SSE contract (assistant)
Events: `plan`, `tool_call`, `tool_result`, `token`, `final` (with evidence refs), `error`. Each event carries `run_id`.

## 5. Execution endpoint rules
`approve` records the decision only. Execution happens in a separate gated service and returns `409` if execution is disabled, the recommendation expired, or its `content_hash` changed since approval.

## Implemented (M3): analytics endpoints

Read-only unless noted. Base path `/api/v1`. **Authentication (ADR 0021):** with `AUTH_JWT_*` configured send `Authorization: Bearer <jwt>` and `X-Org-Id: <organization uuid>` (401 invalid/missing token, 403 not a member or role too low, 400 bad `X-Org-Id`). **Development tenancy (only when auth is not configured):** send `X-Dev-Org-Id: <organization uuid>`
([ADR 0014](ADR/0014-dev-tenant-header-and-production-refusal.md)); production refuses to start until real
authentication exists. Optional `from` / `to` (inclusive dates; default: last 28 days, max 366).

| Endpoint | Returns |
|---|---|
| `GET /dashboard/summary` | totals, KPIs, immature-day count, mature-aligned comparison with the previous period, ACOS driver breakdown |
| `GET /dashboard/trends` | daily points with totals, KPIs and `is_mature` |
| `GET /campaigns?target_acos=` | per-campaign KPIs, health status, budget use, spend distribution |
| `GET /campaigns/changes` | per-campaign current vs previous KPIs with the ACOS driver breakdown |
| `GET /keywords?sort=&limit=` | target performance table (`sort`: spend, sales, clicks, orders, acos) |
| `GET /search-terms?sort=&limit=` | search-term performance table |
| `GET /keywords/findings?target_acos=&limit=` | wasted targets, underperformers, negative-keyword candidates, opportunities (+ full counts) |
| `GET /anomalies` | conversion-rate / CPC / spend episodes over the last 14 mature days |
| `POST /forecasts/account` | backtest, select and **store** a 14-day spend and sales forecast (takes several seconds); 201 |
| `GET /forecasts/account` | latest stored forecast with derived ACOS; 404 if none |

Conventions in force:

- Response envelope `{"meta": {...}, "data": {...}}`. `meta` has `data_sources`, `synthetic`, a MOCK `notice`,
  `as_of`, `latest_date` and `mature_through`.
- Money is integer paise; ratios and percentages are numbers rounded to 4 places; **undefined ratios are `null`**.
- Errors are RFC 7807 problem details; the message is in `title` for HTTP errors. 401 missing/invalid tenant header,
  404 no data, 422 invalid parameters or a period with no mature days or too little history to forecast, 503 no database.
- Response bodies are serialised generically (the OpenAPI document does not yet describe the `data` shapes in
  detail); typed response models are planned with the frontend.
- Not implemented yet: campaign-level forecast endpoints, sync triggers, approval screens in the UI.

## Implemented (M6): recommendations and approval ([ADR 0022](ADR/0022-approval-workflow-and-recommendation-calculators.md))

| Endpoint | Role | Behavior |
|---|---|---|
| `POST /recommendations/generate` | analyst | compute proposals from the analytics; stores new ones as `pending`; idempotent; 201 |
| `GET /recommendations?status=` | viewer | list; every item has `evidence`, `content_hash`, `expires_at`, MOCK notice |
| `GET /recommendations/{id}` | viewer | one proposal with its approval record, if any |
| `POST /recommendations/{id}/approve`, `/reject` | admin | body `{content_hash, comment?}`; the hash must equal the stored content's hash (409 otherwise); only from `pending` and before expiry; identical repeat returns the original with `replayed: true` |
| `POST /recommendations/{id}/execute` | admin | records a blocked attempt and always answers 409 (`execution_disabled`, `not_approved`, `approval_expired`, `content_changed_since_approval` or `no_execution_provider`); nothing is ever sent |
| `GET /executions` | admin | append-only history |
| `GET /audit-logs` | admin | newest first; filters `action`, `entity_type`, `entity_id`; page backwards with `before` (`next_before` in the response) |

**UI:** the Approval Center (`frontend/src/ApprovalCenter.tsx`) lists proposals with their evidence, filters by status, lets analysts generate and admins approve or reject after an explicit confirmation that states nothing is executed, sends the reviewed `content_hash`, and shows the server's reason on 409/403. Until real sign-in exists the role is a development-only menu (`X-Dev-Role`); there is no execute button.

404 unknown recommendation (including another tenant's), 409 not pending / expired / hash mismatch / execution blocked, 422 malformed hash or unknown body fields.
