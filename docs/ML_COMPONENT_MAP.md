# ML Component Map

Audit date: 2026-11-13, commit `b321aff`. Source-first: every entry cites the file that implements it. Accuracy numbers
come from `docs/ML_EVALUATION.md` and `backend/tests/evals/` **[doc]** and were **not re-run** in this audit (the eval
suite takes about 7 minutes for the forecast part and the live-LLM evals cost money).

## 0. Read this first

1. **There is no trained model artifact anywhere in this project.** No pickle, no model registry, no offline training job,
   no feature store. Every forecaster is fitted at request time on the account's own daily series, and every detector
   is a closed-form statistic. "Training process" below therefore means "fit on the history passed in".
2. **Every accuracy figure is measured on synthetic data generated by this repository** (`infrastructure/providers/mock/generator.py`
   and `tests/evals/independent_series.py`). None is evidence about real Amazon accounts. The project's own evaluation
   document says the same.
3. **The recommendations (bid, budget, negative keyword) are not ML.** They are rule-based Python (section 4).
4. **LLMs are not used for any calculation.** They route questions, call read-only tools and phrase cited answers
   (see `AGENT_AND_LLM_MAP.md`).
5. No forecast, anomaly or keyword-finding result has a dedicated screen. The dashboard (`frontend/src/Dashboard.tsx`) calls only
   the KPI, trend, campaign and top-keyword endpoints (`frontend/src/api.ts`). Anomalies, keyword findings and forecasts reach a
   seller only through the API or through the assistant's answers. The Approval Center shows the negative-keyword, bid and budget
   proposals that are derived from them.

## 1. Forecasting models (7)

All live in `backend/app/application/forecasting/models.py`, share the `Forecaster` protocol, see only
`history` (no future leakage by construction) and forecast a 14-day horizon (`HORIZON = 14`).

| # | Model (`name`) | Class | Algorithm | Baseline? | Status |
|---|---|---|---|---|---|
| 1 | `naive` | `Naive` | repeat last value | yes | tested, used in backtest |
| 2 | `moving_average_7` | `MovingAverage7` | mean of last 7 days | yes | tested, used in backtest |
| 3 | `seasonal_naive` | `SeasonalNaive` | same weekday, most recent week | yes | tested; **shipped default** |
| 4 | `seasonal_mean_4` | `SeasonalMean4` | same weekday averaged over 4 weeks | yes | tested; compared as a default candidate and rejected |
| 5 | `ets` | `ETS` | statsmodels Holt-Winters, additive damped trend, additive weekly seasonality (`seasonal_periods=7`) | no | tested; experimental, opt-in |
| 6 | `ridge` | `RidgeForecaster` | scikit-learn `Ridge(alpha=1.0)`, direct multi-horizon on lag features | no | tested; experimental, opt-in |
| 7 | `gbm` | `GradientBoostingForecaster` | scikit-learn `GradientBoostingRegressor(n_estimators=80, learning_rate=0.05, max_depth=2, subsample=0.8, random_state=0)` | no | tested; experimental, opt-in |

**Input features (ridge and gbm)** - `_design()` in `models.py`: one-hot weekday of the target day (7), horizon fraction
`h/14`, value one week back, value two weeks back, trailing 7-day mean, same-weekday mean over four weeks; all divided by
the trailing 28-day mean so one model can learn from series of any size. ETS uses only the raw series. Baselines use the
raw series.
**Output:** a 14-value point forecast per metric (spend, sales).
**Minimum history:** `MIN_TRAIN_DAYS = 60` days plus the 14-day horizon (`service.py:forecast_series`).

**Training process.** `forecast_series()` in `forecasting/service.py`:
1. `run_backtest()` (`backtest.py`): rolling-origin, expanding window, weekly step, 14-day scoring window; typically 7 folds on 117 mature days.
2. `select_model()`: a fitted model wins only if its pooled MAE beats seasonal-naive by `MODEL_MARGIN = 5%` **and** it beats it in more than half the folds. **But** `LEARNED_MODELS_SELECTABLE = False` (service.py), so by default the result is always `seasonal_naive` and every other model's backtest scores are reported as experimental.
3. Intervals: empirical quantiles of the chosen model's out-of-sample relative errors (`INTERVAL_LEVEL = 0.80`), with leave-one-fold-out coverage reported.
4. ACOS is never forecast directly: `derive_acos()` derives it from the spend and sales forecasts, with an indicative range from past fold ratios.

**Evaluation metrics:** MAE, RMSE, MAPE, WAPE (`forecasting/metrics.py`); folds beating seasonal-naive; interval coverage.

**Results [doc: ML_EVALUATION.md sections 4-4e]** (synthetic data only):

| Evaluation | Result | Verdict |
|---|---|---|
| Learned-selection rule on mock seeds 21-25, account level | no worse than seasonal-naive 6/10 (bar 7/10); mean WAPE 12.0% | **failed** (recorded known failure) |
| Same rule on fresh seeds 26-40 | 19/30 not worse (bar 21/30); mean MAE gain -6.7% | **failed** |
| Shipped default (seasonal-naive) on an independently-built generator, seeds 101-120 | mean WAPE 0.294 (bar 0.25); 80% interval coverage 0.779 | **failed** WAPE, passed coverage |
| `seasonal_mean_4` vs seasonal-naive (3 settings, all required) | A pass, **B fail (43% / -3.4%)**, C pass | rule failed; default unchanged |

Conclusion carried by the project itself: the learned models are **not shown to beat seasonal-naive**, and the two synthetic
sources disagree on whether they help.

**Where it is used:**
- Written: `POST /api/v1/forecasts/account` (`api/routers/analytics.py`) -> `forecast_account()` -> `save_account_forecast()` -> table `forecast_runs`. Analyst role; audited as `forecast.created`.
- Read: `GET /api/v1/forecasts/account`; assistant tool `get_account_forecast` (`assistant/tools.py:_forecast`); specialist `performance_prediction` and `ppc_reporting`.
- **Not used:** `forecast_campaigns()` (`forecasting/reports.py`) is called only from `tests/unit/test_forecast_service.py`; there is no endpoint, tool or UI for per-campaign forecasts.
- **Not scheduled:** nothing triggers forecasting automatically. Until someone POSTs, the assistant answers "no forecast exists".

## 2. Anomaly detection (2 algorithms)

Files: `backend/app/domain/anomaly.py` (algorithms), `backend/app/application/analytics/anomalies.py` (use case),
`backend/app/application/analytics/thresholds.py` (parameters).

| Metric | Algorithm | Input features | Output |
|---|---|---|---|
| Conversion rate | one-sided **Bernoulli log-likelihood CUSUM** (`bernoulli_trace`) on per-day (orders, clicks), testing rate fell to 0.6x / rose to 1.5x of the reference rate | daily orders and clicks per campaign; reference = 56 mature days before the 14-day monitor window | Episodes: onset day, peak, first watch day, first alert day, severity (watch/alert), status (ongoing/ended), plus an ACOS breakdown |
| CPC, spend | one-sided **Gaussian CUSUM** (`gaussian_trace`, slack k=0.5) on log values standardised with a **median/MAD** scale (`robust_center_scale`) | daily spend/clicks per campaign | same |

**Training:** none; reference statistics are computed per campaign per request. Thresholds `CVR_H_WATCH=4.7`, `CVR_H_ALERT=6.7`,
`GAUSS_H_WATCH=7.0`, `GAUSS_H_ALERT=10.5` were calibrated by simulating *no change* (`thresholds.py` comments), not from the planted scenarios.
Campaigns with fewer than 500 reference clicks are skipped and reported as `Skipped`.
**Metrics [doc: ML_EVALUATION.md section 3, seeds 11-15]:** detected at watch level 8/10 (bar 8, exactly at the limit); alert 7/10;
median delay 4.5 days (bar 9); false-alarm alerts 0.2 per seed. Only a conversion-rate halving was ever planted; CPC and spend detectors have
false-positive tests only.
**Status:** implemented, tested, integrated, passes its pre-registered bars at the limit.
**Used in:** `GET /api/v1/anomalies`; assistant tool `get_anomalies`; `build_performance_report()`. Not shown in the UI.

## 3. Keyword and search-term findings (statistical, not learned)

File: `backend/app/application/analytics/keywords.py`; math in `backend/app/domain/stats.py`; parameters in `thresholds.py`.

| Finding | Algorithm | Inputs | Output |
|---|---|---|---|
| Wasted target / negative-keyword candidate | exact **binomial lower tail**: probability of seeing zero orders in N clicks at the campaign's own conversion rate; "confirmed" at <= 5%, "watch" at <= 20% (`chance_of_at_most`) | clicks and orders per target or search term, reference CVR from its campaign (or the account when the campaign lacks 100 clicks) | list with level, chance %, projected monthly spend |
| Underperforming target | binomial lower tail of its orders (<= 5%) **and** ACOS above target | orders, clicks, spend, sales | list |
| Opportunity (search term to promote) | **Clopper-Pearson exact one-sided lower bound** of conversion rate at 95% (`exact_lower_bound`, bisection over the binomial tail); ranks by the bound; "strong" if bound >= campaign CVR | orders >= 2, ACOS <= target, not already an exact target or negated | ranked list |

Why Clopper-Pearson: a test showed the Wilson bound ranked 1 order from 1 click above 20 from 100 (`stats.py` docstring, `ML_EVALUATION.md` section 5).
**Training:** none. **Use of mature days only:** `reader.freshness().mature_through`.
**Results [doc, seeds 1-10 and 41-45]:** wasted-target precision 0.67 on the original truth (fail), 0.90 on the restated truth (post hoc; pass);
negative-term "confirmed" precision **0.77 vs bar 0.85 (known failure)**; opportunities recall/precision 0.89/0.94 (pass); against an assumed 30% break-even,
confirmed negatives truly unprofitable 0.934 (pass), confirmed wasted targets 0.821 (bar 0.85, **fail**). Diagnosis in the doc: false positives are weak converters, so a "confirmed" negative means "weak converter worth reviewing", not "irrelevant term".
**Used in:** `GET /api/v1/keywords/findings`; tool `get_keyword_findings`; recommendation generator (negative keywords only); performance report. Not in the UI.
**Unused helper:** `clicks_needed_to_rule_out()` (`domain/stats.py`) is referenced only by `tests/unit/test_stats.py`.

## 4. Rule-based optimisation (deterministic, no model)

File: `backend/app/application/optimization/generate.py`; guardrails in `backend/app/domain/recommendations.py`.

| Type | Rule | Inputs | Output | Guardrails |
|---|---|---|---|---|
| Bid change | new bid = bid x (target ACOS / actual ACOS), factor clamped to +/-20% (`propose_bid_change`) | >= 30 clicks, >= 3 orders, ACOS > 0, enabled non-negative target | `Recommendation` with evidence dict | cap 20% (`MAX_BID_CHANGE_PCT`), change >= 5%, bid >= 1 paise |
| Budget change | +20% for a HEALTHY campaign whose budget cap is hit on most days; -20% for an UNHEALTHY one | `campaign_overview` health and budget-use flags | `Recommendation` | cap 20% (`MAX_BUDGET_CHANGE_PCT`) |
| Negative keyword | every **confirmed** negative candidate from section 3 | keyword findings | `Recommendation` with the evidence | needs text, no numeric value |

Health rule (`analytics/campaigns.py:assess_health`): needs >= 100 clicks; ACOS <= target is healthy, <= 1.3x target "watch", above is unhealthy (`thresholds.py`; target ACOS default 30% is an owner decision, **not learned**).
"Expected impact" is a direction only; no money figure is predicted (`generate.py` module docstring).
**Evaluation:** unit tests (`tests/unit/test_recommendations.py`, 395 lines) and the project's 33-check end-to-end run **[doc]**. There is **no accuracy evaluation** of whether these proposals improve outcomes, and none is possible on synthetic data.
**Used in:** `POST /api/v1/recommendations/generate` -> table `recommendations`; Approval Center UI.
